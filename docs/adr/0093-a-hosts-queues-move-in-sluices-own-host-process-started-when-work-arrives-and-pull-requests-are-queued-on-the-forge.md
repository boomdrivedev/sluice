## Context and problem statement

Record 0068 kept sluice a plain command line that needs no daemon and let a host run one driver, `sluice run`, by its own choice. A host that wants every queue moving runs one per repository; the gate box runs five under systemd, and the user called that design one that "just doesn't scale". Record 0092 proposed one host driver for every repository, still a service a host keeps. Meanwhile every waiting submit and wait on a host runs rounds where no driver lives, so ten agents' submits are ten processes each trying to form the branch's next candidate, and the host's bound on runs is counted across processes through files. And a branch that takes pull requests is taken in by whichever host holds an intake mark on the forge, with its renewal, its lease, hand-overs and their withdrawals.

## Considered options

1. **One host process, sluice's own.** The first command that needs the host's queues moved starts it where none answers; it holds every repository on the host that has sluice, each repository's queues apart, and the host's bound on runs in one place, and ends once no queue has work in play and nothing follows it.
2. Record 0092: one host form of `sluice run`, which a host's service manager keeps. One service in place of one per repository, but still a service each host installs and keeps.
3. One process per queue, started by its submit. Ten submits to ten branches are ten processes, and the host's bound and the forge's allowance are coordinated across them through files.
4. Every command runs rounds itself, as a waiting submit does today. Nothing new runs, but ten waits are ten processes forming one branch's candidate.

## Decision outcome

Option 1.

- **Nothing is installed.** sluice is a binary on the path. A command that needs the host's queues moved, a submit among them, reaches sluice's host process over a socket in sluice's state folder, or takes the lock and starts it when nobody answers. A submit adds its entry and returns at once; `sluice wait` follows the process for whoever wants to watch (135).
- **One process per user on a host.** It holds a task for each repository with work, each repository's queues apart, so a refusal or a slow fetch in one holds no other's round (26); one scheduler keeping the host's bound on runs, a queue's candidates before sessions' runs (71, 150); and one forge client, one allowance. Its concurrency is the language's, inside one process, never processes coordinating through files.
- **Gone when idle, and nothing lost.** It ends once no queue it holds has work in play and nothing follows it. It keeps nothing the records do not hold, so a crash or a sleeping laptop loses nothing: the next command that finds work in play and no host process starts one. It finds its repositories in an index sluice writes in the host's state whenever any command of sluice's finds a repository has sluice, a policy at a revision the host holds or records, the user's choice. A run outlives the process that started it and is equipped from its repository's policy (147). A command of a newer sluice has an older process hand its repositories over and end (135).
- **The reader is the host process.** A watch or a wait that finds no reader starts the host process, which reads, and follows it (129).
- **No intake mark.** The intake mark, its renewal and lease, hand-overs and their withdrawals all go (120, 140). Whatever executes a branch's queue takes its requests in. A host's submit opens or updates its request and marks it ready, and the host follows it by the forge's state and sluice's check on its head, its status showing the request's entry there as fields (137, C.5).
- **Where a queue runs.** Each branch's queue runs whole in one of four ways, behind one contract with Flume, as the amendment of 2026-11-08 below has it.
- **sluice calls no other program.** Flume reads each outcome at its settles; its step per settle is nothing (flume C.6).

## Amendment of 2026-11-08: one contract with Flume, and a queue runs whole in one of four ways

sluice keeps one contract with Flume and the Boomdrive runner however a queue runs, and each branch's queue runs whole in one of four ways: with no daemon, by a daemon on this machine, by a daemon on another machine, or by a GitHub Action. Status: accepted by the user on 2026-11-08, on their card ("Approved"), and point 3 as it reads now on their card the same day ("Yes: machines choose how sluice runs, the repository says what must pass").

Deciders: the user, 2026-11-08, in agentplot-ops's pane, as agentplot-ops relayed it (signal 2026-11-08-agentplot-ops-134a1434/01). They asked for sluice's direction to be handled as two separate things. The first is how sluice works with Flume and the Boomdrive runner: `sluice submit` starts the background processes, and sluice reports to Flume when the work is done, so Flume marks it and launches a fix. The second is local against remote execution, which doesn't change the first: "It seems like the GitHub job idea, just for doing the pushes to main and not for running the test, is a [...] band-aid from a design perspective. In my mind there's going to be local execution and then there's going to be remote execution but that doesn't change."; "I think we need to support either a daemon running on the same machine or a different machine, or a GitHub action". The same day, refining it (signal 2026-11-08-agentplot-ops-77e3a93c/01-sluice-runs-four-ways): "I'd argue that it's really four options because sluice runs on the same machine as a background process that gets kicked off. We did that to avoid the daemon but let's face it: a remote executor is a daemon. What stops you from running a daemon on the same host or a remote host? It's kind of the same thing but sluice should also be able to run without a daemon". Reading the plan that followed, the same day: "Why would it be the responsibility of a repository to know how its surrounding infrastructure is actually set up?" agentplot-design for writing it into this record and the statement, and for the choices marked as its own.

1. **Two concerns, kept apart.** How sluice works with Flume and the Boomdrive runner is one concern, and where a branch's queue executes is another. A change to one never changes the other.
2. **One contract, wherever the queue runs.** `sluice submit` adds its entry and returns at once, having started whatever background work the way that executes its branch needs. Once the submission is decided, sluice reports its outcome to its submitter as this record has it (the notice, `sluice inbox` and `sluice wait`), and Flume reads that report, marks its place, and launches the kind's landing fix on a kick-back (flume record 0056; weir record 0005). sluice still calls no program of Flume's. The user's "sluice report" is this report. Whether it is also a command of its own is the build's choice, and it changes nothing of the contract.
3. **A queue executes whole, in one of four ways, and the machines choose it.**
   - **No daemon.** The submitting machine's own sluice process executes it: `sluice submit` starts it, and it ends when idle (135, as decided above). sluice works this way with nothing set.
   - **A daemon on this machine.** The machine keeps `sluice daemon` running. That is the same host process, which never ends when idle.
   - **A daemon on another machine.** That machine keeps `sluice daemon` running, and it runs the queues of the repositories it holds.
   - **A GitHub Action.** GitHub Actions' jobs execute it: they take the requests in, run the checks on GitHub's machines and push the landing. The repository carries the workflow GitHub runs. This is the one thing any way puts in a repository, since GitHub runs only jobs a repository defines.

   No setting chooses a way. A daemon is a command a machine keeps running by its own choice. The repository says only what a landing must pass and whose test results it accepts: its gate and its signers. Those stay in the repository because a machine can't vouch for itself, and the branch's own revision is what is read, so no change loosens its own checks (core.15, 78). A shared branch's queue runs where its results count. A machine whose signature the branch does not accept leads none of its rounds and runs none of its checks. It submits, and leaves the queue to one whose signature the branch accepts.

   Whatever executes a branch's queue takes its requests in, forms and tests its candidates, and lands them. Nothing does one part of that while another does the rest. No request is taken in by two ways, two machines or two copies of one repository.
4. **Not taken.** A forge's jobs taking requests in and landing them while machines run the checks, the split the user called a band-aid. A branch on GitHub Actions runs its checks there too, and the change that built the split is reverted whole on its bolt (`sluice-runs-one-host-process--takes-out-the-forge-round`).
5. **What stands.** Everything else above stands: one host process per user, started when work arrives and gone when idle, as the no-daemon way, with nothing installed on a machine that uses it. So does the removal of the intake mark, its renewal, its lease and its hand-overs. Whatever executes a branch takes its requests in.
6. **Consequences.**
   - sluice runs standing only as a daemon a machine keeps running by its own choice, on this machine or another (point 3). That settles wldn's question of a machine whose signature a branch's tests need: that branch executes by a daemon on that machine, which stays up.
   - Rules core.31 and core.33 are amended to match, each marked proposed.
   - The statement's clauses 135 and 137 and C.8's table follow, marked proposed (agentplot/blueprints, design/sluice/requirements.md).
   - Left to the build, within points 2 and 3 (agentplot-design's choice): how a machine's service manager keeps `sluice daemon` running, and what a machine whose signature a branch does not accept starts when it submits. Units are queued from this amendment.

## Amendment of 2026-11-13: every read of a queue follows the host process, and a result is read once

agentplot-design's, drawn from clauses 69, 109 and 129. On chuck-herdr-alpha under sluice 0.93.2, each one-shot overview fetched its repository from the remote under one lock and loaded the whole results history, about 60 MB, so waits that read it missed their 10-second bound (signal 2026-11-13-swb-7-ops-ca607be7/01, wldn's).

- **Every read follows the host process.** A status, an overview and a forecast are answered from the host process's last reading, as a watch and a wait are, and fetch nothing of their own while it has read within its tick. One that finds no host process starts it and is answered from its first reading. The remote is asked once a tick for every branch the host reads there (129). Record 0056's one-shot overview, which read the records itself, is amended so.
- **A result is read once.** The host process reads each recorded result and each signed run record once, verifying each signature once, and answers a gate or a status by the keys it asks for. No read loads or verifies the whole history again, so a read costs what it asks for, however long the history grows.
- **No result is taken away with its branch.** A result belongs to its key and system, not to a branch (69); a signer's records are only added to (109); a landing reads its verdict again from them (C.6). A branch that lands or is removed keeps every result it recorded. Pruning a landed branch's results was the other path: it would take away passes other branches' gates count and evidence a landing names.
- Rule core.25 is amended to match.

## Amendment, 2026-11-13: what the build of the host process chose

Status: accepted on 2026-11-13 as the choices of the change `one-sluice-process-runs-each-hosts-queues`, its design D1 to D17 and D25 and its code stage, each within the decision and its amendments above and cheap to change.

Deciders: the design and the code stage of the change `one-sluice-process-runs-each-hosts-queues`.

Sources: the statement's clauses 64, 69, 71, 88, 109, 129, 133, 135 and 150, S19 and S75; records 0063, 0087, 0107, 0119 and 0123; rules core.4, core.22, core.25, core.29, core.31 and core.49; the change's design D1 to D17; `crates/sluice/src/host_process/`, `crates/sluice/src/profiles/records.rs` and `crates/sluice-core/src/step.rs`.

### Decisions

1. **The socket is in the user's own short directory** (D1). The host process binds `host-<digest>.sock` in the user's directory that record 0063 makes and checks, named by a digest of the state folder's real path, so each state folder has its own process and no socket's path passes macOS's 104 bytes however deep the state folder lies. *Not taken:* the socket under the state folder's `host/`, as the decision words it, which a test's or a sandbox's deep state folder makes too long to bind.
2. **`sluice run` is kept, hidden, as a follower** (D11). It checks the host's systems, says once on stderr that sluice starts its own host process and nothing needs it, and prints each pass of the host process as a pass of its own printed it; `--rounds` counts the passes it followed. It takes up a change of `[telemetry]` alone, by starting itself afresh, carrying the passes it followed and what it said. *Not taken:* removing the command, which turns each host's unit that runs it into a restart loop until the unit is retired; dropping its take-up, which leaves a follower sending to a collector the file no longer names.
3. **`sluice step` is the host process's round** (D10). The step asks the host process for one round of the branch, which runs between the repository's passes as a pass's does: the remote's one ask, the branch's intake, the round, and what the round sent back of a pull request shown where it stepped (decision 23). It prints the document a step printed. *Not taken:* a step that runs its round in its own process beside the host process's passes, two processes acting on one branch's round loop (core.14); a step with no ask of the remote, whose landing reads each signer's runs as the last pass fetched them, so a run another host signed since reads as unsigned and its combination is tested again at every step.
4. **Passes when asked, for the tests** (D14). Under `SLUICE_ROUND_SLEEP=record`, the value the tests already set to skip pauses, the host process takes no pass of its own and passes only for a `pass` or a `step`; its `hello` says so, and a follower then asks a pass at each of its own ticks, whatever its own setting. *Not taken:* a setting that keeps the host process from starting, with waits running rounds as before, a behaviour 135 removes kept behind a flag (core.12); a follower reading the mode from its own environment, which leaves a watch of a host process an earlier test command started reading nothing new.
5. **The look runs on a thread of its own for each repository** (D4). At its start and every three seconds the host process looks at each repository in its index it holds no task for, each look on a thread of its own under the round's retry policy, never on the loop that accepts connections; a repository still being looked at is passed by. *Not taken:* the looks on the accepting loop, where a remote slow to answer holds every command's connection.
6. **A newer command waits out an older process's hand-over** (D8). A command whose version is newer asks the older process to hand over, then waits for its lock to go for as long as the process gives its tasks to finish their rounds and a start's ten seconds after, and only then starts its own; an older process still running then is an error naming its log. *Not taken:* a start's ten seconds alone, which an older process still finishing a round outlasts.
7. **A part is held from the count to the start, and a start refused at the bound starts nothing further** (D12). A round holds each run's part of the host's bound before it writes the decision that marks the run starting, keeps its parts through its landing, releases and outcomes, and hands each to its start; a start the check seam refuses at the bound opens again each run decided behind it, its part dropped and no place made. A run a lead marks starting under the claim it gives a pool's job holds no part of the lead's host: the job's own round holds its run's part as it starts it, and a run launched on a pool holds none at all. The check seam's `hold` names no repository: the check profile is bound to its repository and names it to the host's room. *Not taken:* the room counted when the round decides and admitted only at the start, the two steps the decision ends; a pool's run counted against the lead's host, which it never runs on.
8. **Each repository keeps its own forge client.** Each repository's task binds the repository afresh, its forge client among it; the allowance's pause stays one for the host, in the host's state (134; rule core.29). *Not taken:* one forge client shared by every repository's task, a change of its own.
9. **A records list the pass cannot read is the reader's document.** A pass whose read of the branches' records fails writes the failure, in the words it was refused with, as the document every watch and wait follows, and reads the records again at its next pass. *Not taken:* failing the pass, which leaves every follower reading the last document as though nothing failed.
10. **A one-shot read sends `read` and reads held** (D16). A status in each form, a one-shot overview, the home view and a forecast send `read {repository}`, starting the host process where none answers, and then read with the core held: every branch through the records as the host holds them since the host process's last ask, the branch's revision with no fetch, the records seam's `hold` listing the branches and the hosts' signs of life from what that ask fetched, and a round refused under it. *Not taken:* running the read inside the host process over the task's binding, which holds a read behind a landing for minutes and sends its warnings to the host process's log; a read that fetches for itself where the reading is stale, today's cost.
11. **A reading is marked as it begins and ends, spanning a pass** (D16). Each pass and each look marks the repository's reading as it begins and as it ends, with the words a remote refused it with. A reading is current where it ended within a tick, three seconds, or where one under way began within a tick of the last one's end, so a status during a long landing is answered at once from the reading before it; and in either case only where it began after the last `serve` a command sent for the repository, `branch delete` among the commands that send one (D15), so a read after a change reads it. Where none is current, the task's next pass reads, woken at once, or the look where no task runs; under passes when asked, the look, which runs no round. *Not taken:* a reading current only once ended, which holds every status behind a landing; a reading current for its tick whatever a command changed since, which shows a branch removed on the host as present in an overview whose status says it is gone (core.11).
12. **A read waits the round's retry bound and a tick** (D16). The host process waits for the reading it asked for for the round's retry bound and a tick, and the command for that and a tick more; past it, the command reads as the host holds the repository and says on stderr when the host process last read it. A current reading whose ask a remote refused is said on stderr in the remote's words, the records read as last fetched. *Not taken:* waiting without end for a host process held in a look a remote does not answer; reading held with nothing said, which hides that the remote could not be asked.
13. **A one-shot overview prints the reader's document** (D16). Where the repository's reader keeps its tick once the reading is current, a one-shot overview prints its document and the home view counts from it, the text rendered from it as the watch's is; where none does, or a look made the reading, which writes no reader's document and which the `read` answer names, they render the records as the host holds them since the reading, with the pull requests as the host last kept them. *Not taken:* a look that writes the reader's document, which takes the reader's lease from a pass; the records rendered beside a current document, which prints an overview no reader wrote.
14. **Every forecast forms on what the host holds, and asks afresh once** (D16). A forecast sends `read`, answered at once beside a reader that keeps its tick, and forms from the reader's document where it holds what the forecast forms from, otherwise on the records and every branch as the host holds them, fetching nothing. Where the host lacks a revision it forms from, it sends `read` with `afresh`, answered once a reading begun after the ask ends, and forms again: a branch of which that reading, current and refused by no remote, brings no revision to the host is no branch, refused as a forecast refuses one, exit 2; what is still lacking otherwise is a read it could not make, exit 3. *Not taken:* fetching what is lacking, the cost the reading removes; a forecast beside a ticking reader whose document lacks the branch reading as a round reads, which fetches; every branch the host lacks read as a read it could not make, which says a branch that exists nowhere could not be read.
15. **Results are asked for by what the caller reads** (D17). `State::results_for(branch, &ResultAsk)` answers every line whose key, combination or task the ask names; a landing's second reading asks the combinations it lands, then their keys, which a pass elsewhere may prove. An ask for every line is kept for a test's inspection of the log, which no step, gate or command makes. *Not taken:* a way for each test's rig to read its log whole beside the seam.
16. **The host process keeps an index for each results log** (D17). One for the repository's own log and one for each remote's replays beside it, kept for the process's life and found by the log's path, each read from its offset, read whole again where the file shrank or was replaced, and each signer's ref read by entry, a blob verified once for each key digest. The tick's ask fetches each signer's runs, and a push of a signer's runs is read here as fetched, so a round reads its own signed runs with no fetch. Each answer that verified a record says how many in the host process's log. *Not taken:* one index holding every log of the repository; a fetch of the signer's ref at each read, which a command made before.
17. **A command asks with `results`, answered on the connection's thread** (D15, D17). A command's records profile sends `results {repository, branch, wants}`; the host process answers on the connection's own thread from its index, through a binding of its own that reads every remote as the last ask fetched it, with no wait on the repository's task. A command whose host process cannot be asked reads the results itself and says so on stderr. `sluice status <n> --json` gives `checks`, the rows of the combination the submission was last tested in, read from that combination's results alone. *Not taken:* answering through the repository's task, which holds a status behind a pass; failing a command whose host process cannot be asked, which a host process of an older sluice that knows no `results` would make every such command do.
18. **A follower is told of the passes begun after it came** (D9). A wait's or a watch's follow asks a pass at once, outside passes when asked, and is told only of passes begun after it came, its first tick waiting for that pass within the read's bound; so a wait out of time returns its submission as that pass left it, and a watch's first line is that pass's document. *Not taken:* a follower told of a pass under way when it came, whose document may come before what it follows; a first tick that reads what is there, which returns the record as it stood.
19. **A pass asked of a test's host process is at its asker's time** (D14). A `pass` names its asker's time, and a host process that passes only when asked takes that pass at it, moving on by a tick only where none is named. *Not taken:* a tick for every asked pass, which two waits asking passes drive at twice their pace, its reading reading what falls due at that pace; the later of its own time and the asker's, which leaves a command started after an earlier one's passes behind the host process's time, so nothing falls due for it.
20. **A check profile beside the host process holds through its socket** (D12). A check profile bound with no room holds its runs' parts of the host process's room over its socket, the process started where none answers; the host process binds its own room into each repository's binding, and a test that starts runs in its own process binds a room over its own count. A combination's hold over the socket is answered once, held or refused, as a round's own ask is, and counts as no session's wait. *Not taken:* a room of the process's own over the host's registry, which decides a part outside the host process.
21. **A step leaves a repository an older `sluice run` drives to it** (D7, D10). A step's round, like a pass, runs only where the repository's task holds its driver's lock; beside an older run that holds it, the step is refused, naming that run. *Not taken:* a step's round beside the older run, which the branch's lock keeps safe but which rounds a repository the older run drives.
22. **A wait follows its request across hosts by the branch's records** (D25). A follow reads, with nothing written, whether the branch's records are on its remote and name another host as their lead, or none yet, and follows the request across hosts where they do, waiting to be taken in by that host, at the host's one pace through the kept follows. *Not taken:* knowing another host keeps the branch only from this process's intake, which a wait runs none of.
23. **A pass shows what a round that stepped sent back of a pull request** (D5, D10). A submit's request whose submission the round failed or found in conflict is marked a draft and shown held for the next submit before the pass writes the document a wait follows, as the wait's own intake did once a round had run. What the round sent back is told by the entry the host keeps of each request against its submission now, and the request is the one the pass's intake listed, so nothing is asked of GitHub but a request's timeline the host keeps none of: no list and no query (136; rule core.32). The round's delivery posts the outcome and the comment, and a request opened by hand, which no submit holds, keeps its `failed: ` check, so a host following it names the blamed check; a submit's request is read on another host by its draft mark. When the branch's requests were last asked for stands, so a pass after a landing still asks at once, and a request's move to testing is posted by the next pass's intake. *Not taken:* the round before the intake, which takes a request's submission in a pass late; a wait that reports a request sent back before it is a draft, its comment saying sluice marked it one; the branch's whole intake run again after the round, which asks GitHub for the list and the query a second time in one pass, posts every move a pass early and shows a request held on another host before any host could read it failed; a wait that waits a pass more for a request it follows to be marked a draft.
24. **A wait meets a spent allowance only on the request it follows** (D9). A wait runs no intake, so the one read of GitHub it makes is of a pull request it follows; there it waits the pause out within its limit (134). A wait on a submission meets none: the host process's pass passes the forge's part by, and the submission lands or not as its round finds it. *Not taken:* a wait that reads the pause and waits it out though it calls nothing, which holds a landing's report behind a pause it never met.
25. **The host process writes only through the folder it holds** (D1, D6; the code stage of the fix `a-new-state-folder-test-passes-under-load`, 2026-11-15). It opens `host/` as it starts and names every file it opens, makes or moves there after through that open folder: its lock, version and log, the index's lock and list, the idle end's start lock and a hand-over's. A write made as the folder moves lands in the folder that was its own, never in one made again at its path, whichever thread makes it; the folder's device and inode, which tell it the folder is gone, are read from the folder held. A command's index opens the folder its path names for each call and takes its lock and writes there. Found by the bolt's verify at bbc6a183, where an answer noted its repository after the test had made the folder again, writing `start.lock` and `repositories` into it before the next tick ended the process. *Not taken:* a look at the folder's device and inode before each write, which leaves a window between the look and the write that a loaded host falls into; an answer that notes nothing once the process is stopping, which leaves the same window before the next tick marks it stopping.

## Amendment, 2026-11-18: what the build of the daemon chose

Status: accepted on 2026-11-18 as the choices of the change `sluice-runs-as-a-daemon`, its design D1 to D13. Each is within point 3 of the amendment of 2026-11-08 and the amendment of 2026-11-18 above, and cheap to change.

Deciders: the design and the code stage of the change `sluice-runs-as-a-daemon`.

Sources: the statement's clauses 129, 135, 137 and C.8; records 0098 and 0107; rules core.31, core.51 and core.54; boomdrivedev/boomdrive's `nix/modules/darwin.nix`, `nixos.nix` and `activate.sh`; `crates/sluice/src/host_process/`, `crates/sluice/src/hand_over.rs` and `nix/modules/`.

### Decisions

1. **The daemon is the host process with its idle end off** (D1). `sluice daemon` runs the host process in a daemon mode whose loop never ends for being idle. Everything else is the host process's. Its `hello`, `host/version` and the overview's `host_process` say `daemon`. *Not taken:* a daemon that follows the host process as `sluice run` does, so the process the service manager keeps is a follower and the host process a detached one it neither started nor stops.
2. **A daemon takes the host from a host process that ends when idle, and waits behind another daemon** (D2). A holder that is no daemon, whatever its version, is asked to hand over and waited for as a newer command waits. Where it still lives then, the daemon exits 3 naming the log. A holder that is a daemon is asked nothing: the daemon says once which daemon it waits for and blocks on the lock. It takes the lock only once no start holds the start lock, so a daemon starting afresh in place keeps its place. While a holder that is no daemon hands over, the daemon holds the start lock, so a command meanwhile reaches the daemon. *Not taken:* ending at once as `sluice host` does, which a service manager restarts in a loop; asking another daemon to hand over, so two daemons trade the host back and forth.
3. **A daemon hands over by starting afresh in place** (D3). Asked to hand over, a daemon lets each task finish its round, lets its lock and socket go, and replaces its image with the asker's executable running `daemon`, with the environment it started with. `hand-over` names the asker's executable, read as absent from an older command, when the daemon starts afresh as its own. *Not taken:* starting afresh always as its own executable, which a newer command finds older again at every command; a newer command using an older daemon as it is.
4. **A command tells the daemon started afresh by its `since`** (D4). After asking a daemon to hand over, a command waits for a host process that is not the image it asked: another pid, or the same pid with another `since`, written to the millisecond. It fails naming the log where the image it asked still answers, and starts its own where none answers. *Not taken:* comparing versions, which a host's own build of one version cannot pass; a field of its own for the image.
5. **A settings change a daemon cannot take up in place is a start afresh in place** (D5). The daemon starts afresh as the executable it started as, in place of the detached successor record 0107 as amended 2026-11-13 has a host process start. Where the start fails, it takes its lock and socket back and goes on, said once. *Not taken:* a detached successor, which ends the process the service manager keeps.
6. **The start lock is carried across the start afresh** (D6). The daemon holds `host/start.lock` across its `execve`, the descriptor named in `SLUICE_START_LOCK_FD`, which `main` takes out of the environment first. The image started afresh lets it go once its socket answers. *Not taken:* letting the lock go at the `execve`, so a command in the gap starts a host process the daemon then has hand over.
7. **A signalled daemon stops as a hand-over does** (D7). `SIGTERM` and `SIGINT` end it, each task finishing its round, its lock and socket let go, exit 0. Its runs outlive it. The services give it 75 seconds, the tasks' time to finish and a margin. *Not taken:* ending at the signal, which leaves a round half done for the next host process to settle.
8. **A daemon started in a repository notes it in the index** (D8). It notes its working folder's repository where that has sluice, as every command does, and needs none to start. *Not taken:* repositories named on its command line or in the module, which "Index, on any sluice use" leaves out.
9. **On nix-darwin, a launchd agent copied from Boomdrive's runner's** (D9). `launchd.user.agents.sluice` runs `sluice daemon` once the store is mounted, at load and kept alive, a stop ending the daemon alone, its early words in `~/Library/Logs/sluice-daemon.log`. *Not taken:* a launchd daemon of the system, which runs apart from the user whose index and state it serves.
10. **On NixOS, a lingering user's unit restarted by the user's activation** (D10). `systemd.user.services.sluice` runs for `services.sluice.user`, who lingers. The user's activation starts it, or restarts it where its command line changed, since NixOS restarts no changed user unit. *Not taken:* a system unit with `User=`, which runs apart from the user's manager, so the family's tools are kept two ways.
11. **The service runs the module's sluice** (D11). Its program is the package's `bin/sluice`, so a new package restarts it. With no package, it runs the `sluice` its `PATH` finds. *Not taken:* a bare `sluice` always, which no new package restarts.
12. **One option** (D12). `services.sluice.daemon.enable`, false, declared only with `services.sluice.enable`. A host that moves the state folder gives the service the same variable through the service's own options. *Not taken:* options of the module's own for the daemon's environment, repositories or log.
13. **`sluice run`'s line names the daemon** (D13). Its one line on stderr says `sluice daemon` keeps the host process running on a machine that chooses to. It stays hidden and a follower. *Not taken:* removing `sluice run`, which waits for gate boxes to retire their units.

## Amendment, 2026-11-19: where nothing is in play, a repository's remote is asked once a minute at most

Status: the decision is clause 129 as boomdrive-design amended it on 2026-11-19, on the user's word that day to fix deneb's host process now (boomdrivedev/blueprints 8fbd5cc). The points below are the code stage's own choices within it, each cheap to change, with the path not taken.

Deciders: boomdrive-design, on the user's word of 2026-11-19; the code stage of the fix `main--the-idle-repository-asks-once-a-minute` for the choices below.

Sources: the statement's clauses 129 (as amended 2026-11-19), 135 and 136; record 0108 (as amended 2026-11-19); rules core.25, core.31 and core.32; the change `an-idle-repositorys-remote-is-asked-once-a-minute`.

On deneb, sluice 0.97.5's host process asked every repository's remote every three seconds, idle repositories among them. Decision 5 above has it look at each repository it holds no task for at its start and every three seconds, and each look fetched the remote's records; a watched repository's task fetched them at every pass, a second apart. Each fetch from GitHub was made as app 5719968, so idle repositories alone spent its allowance.

### Decisions

1. **The minute counts from the last ask of the repository by any reading of the host process's.** A look and a pass of the repository's task mark their reading in the repository's marks (decision 11), and those marks now also hold when a reading last began that asked the remote, whether the last reading found work in play, and when an ask was last called for. Whether a reading asks is decided as it begins, under the marks' lock. *Not taken:* a minute kept by each binding or each thread, under which a look and a task each ask within it; a slower scan alone, which leaves a watched task's passes asking every second.
2. **Whether work is in play is the last reading's finding.** A reading asks where the last reading found work in play. The pass that lands is in play as it begins and asks. The pass after one that emptied the queue asks nothing within the minute, since the landing is the host's own write and its records hold it. *Not taken:* asking at the pass after a landing, which asks for what the host already holds.
3. **Every command that tells the host process of a change asks at once.** A submit sends `serve`, and so do an amend, a withdrawal, a set-aside, a push, a release and a branch's creation, acceptance or removal. A reading that begins after any of them asks, as one begun after a `serve` is the only one current for a one-shot read (decision 11). *Not taken:* a submit alone, which would have the host process tell those changes apart, each the host's own move.
4. **A watch's opening, a forecast's second ask and a binding made afresh ask at once.** A watch's follow marks an ask due before it wakes the pass it asks for. A forecast asks a reading afresh only where the host lacks what it forms from, which only an ask brings. A task's binding, made as it starts or under settings taken up, has asked nothing, and one that has asked nothing lists a remote's branches by asking it. A wait's opening is no such call: its submission is in play, so its pass asks, and one whose submission is not reads the remote within the minute. *Not taken:* a wait's opening asking whatever is in play, beyond the clause's list.
5. **Between asks, a reading reads each remote as the last ask fetched it.** The look holds its binding, as a one-shot read's is held. A task's pass leaves out the remote's ask on a binding that has asked, and reads the remote as fetched. A reading that asks nothing keeps the last ask's refusal as its words. *Not taken:* holding the task's binding, which would have its rounds read the remote as last fetched.
6. **A one-shot read stays current within its tick.** Past its tick, it is answered by a pass or a look as before, which asks the remote only where it is due, so a status between asks reads the host's own files afresh and the remote as last asked. *Not taken:* a reading current for the minute, which would answer a status a minute behind records in the host's own files, previews and places, none of which need an ask.
7. **The host process goes through its index every three seconds, and looks only where an ask is due.** Pruning the index and draining the room's waits keep their three seconds. *Not taken:* a minute's scan, which would leave a repository whose task ended waiting up to two minutes for its next look.
8. **Where passes are taken only when asked, every reading asks** (decision 11's D14). Each pass and look is a command's ask there, so a test's two hosts read each other's work at each pass their commands ask for. *Not taken:* the minute there too, which would hold a test's second host a minute behind the first.
9. **Nothing lists a remote's branches by asking it ahead of the reading's one ask.** The index's prune as the host process starts reads each remote as last fetched, as its own doc said it did, and a task that passes at its tick reads what is in play at its first pass, which asks, rather than as it starts. Found by this change's test on the host process: each made a binding that had asked nothing list the remote's branches by `ls-remote`, so a start and a watch's opening each asked the remote twice. Where passes are taken only when asked, a task still reads what is in play as it starts, since no pass of its own follows. *Not taken:* a seam call listing the branches as last fetched, beside `State::hold`, which a fresh binding's look already uses.

## Amendment, 2026-11-21: sluice host runs on a tokio edge

Status: accepted. The user approved the change `sluice-host-runs-on-a-tokio-edge` on 2026-11-21. The points below are the build's choices within it.

Deciders: the user, on 2026-11-21. The build of the change `sluice-host-runs-on-a-tokio-edge` made the choices below.

Sources: `tokio-streams-before-rxrust@0b9fc11cda8b`, `one-read-in-flight@e99acda774d0`, `never-break-an-existing-client@ed293965fc5c`, and the change `sluice-host-runs-on-a-tokio-edge`, design D1 to D6.

### Decisions

1. **A tokio runtime runs in `sluice host` and `sluice daemon` alone.** Before: the host process ran on threads, and a thread answered each connection. Now: a runtime with many threads holds the socket, the connections, the signals, the timers, the file events and a scheduler for each repository. Its pool for blocking work has at most 256 threads. The core, its seams and each command stay synchronous. *Not taken:* async seams in the core.
2. **A worker holds each repository's binding on a thread of its own.** Before: a thread for each repository looped over its passes at its tick. Now: the scheduler decides when to read. The worker passes when its scheduler asks. The binding holds values that stay on one thread, so the worker keeps it. The worker thread enters the runtime, so it reads tokio's clock. It is no task of the pool for blocking work, because a paused clock does not move while such a task runs. *Not taken:* a worker on the pool for blocking work.
3. **Triggers during a reading make one more reading.** Before: a command's read waited in a loop that slept 20 ms. Now: each repository's readings go on a `watch` channel. A trigger marks a reading due. Many triggers during one reading make one reading after it. The reading in flight answers a one-shot read that comes during it, as it ends. Where a command told of a change after that reading began, one more reading answers the read. A pass and a look never run at once. A look runs beside work of the worker that is no reading, such as a step. Each moment of a reading has a number in order, so two moments that a paused clock gives one time stay apart.
4. **File events start a reading of a repository with nothing in play.** Before: the host process looked at each repository in its index every three seconds, and a watched repository passed each second. Now: notify-debouncer-full 0.6 watches the git common folder for `packed-refs`. It also watches `refs`, each worktree's `HEAD`, the records, and each branch's folder in the records. The debounce time is 200 ms. The watch joins the debouncer's flushes that come less than 120 ms apart into one burst. While work is in play, the worker passes at its tick. File events start no reading then, because most of them are the host's own writes. A reading of each idle repository at least once a minute is the backstop for a change no event reported. *Not taken:* watchman, and a debounce of futures-time.
5. **File events tell of the state folder, the index, the settings and the runs.** Before: the host process looked every 100 ms at its state folder, the room and a daemon's stop flag. It looked at the settings file every second. Now: a watch of the state folder, of `host/` and of the settings file's folder starts each of these looks. A watch of the registry and of each counted run's folder tells of a run that ended, and frees its part of the bound. The minute's backstop also does each of these looks. It finds a run whose supervisor ended with no result. A session's wait for room asks the room again when the room changes and when a combination's wait lapses.
6. **`SIGTERM` and `SIGINT` stop each host process as a hand-over does.** Before: only a daemon read these signals, from a flag at its next look. A host process that a command started ended at once on them. Now: every host process reads them as they come. Each scheduler finishes its reading and lets its worker go. The process lets its socket and its lock go, and exits 0.
7. **A daemon that starts afresh keeps its socket.** Before: the daemon removed its socket, and the image started afresh bound a new one. Now: the daemon hands its socket to the image started afresh by its descriptor, in `SLUICE_SOCKET_FD`, beside its start lock. A command that connects meanwhile waits in the socket's queue. An image that gets no socket binds one, as a start does.
8. **A successor says that its socket answers.** Before: a host process that handed over asked every 20 ms, for ten seconds at most, whether its successor answered. Now: it gives its successor a pipe, named in `SLUICE_READY_FD`. The successor writes to the pipe once its socket answers. The pipe's end, where the successor ends first, also ends the wait.
9. **An idle host process lingers for 100 ms.** Before: the host process looked every 100 ms at whether it was idle. Now: the end of a connection starts that look. So do the end of a scheduler's work and a change of the room. A host process that is no daemon ends after 100 ms with nothing to do. A command that closes one connection and opens the next meets the same process, as before. In a test that passes only on a command's ask, a file event reads no repository that a worker holds. The backstop reads none either. The look passed such a repository by.
10. **The protocol stays as it is.** Each request and each answer is the same, line for line, so each released command keeps working.
11. **Two waits still look again.** A daemon that waits behind another daemon looks at the host's lock every 100 ms, on a thread of the pool for blocking work. It is not the host process while it waits, and a signal ends the wait. The debouncer's own thread looks at its events at a quarter of the debounce time.

## Amendment, 2026-11-21: sluice host owns its workers

Status: accepted. The user approved the change `sluice-host-owns-its-workers` on 2026-11-21. The points below are the build's choices within it.

Deciders: the user, on 2026-11-21. The build of the change `sluice-host-owns-its-workers` made the choices below.

Sources: `workers-end-with-their-owner@292e869158d6`, `sluices-runs-end-with-its-host-process@e814b716f3b1`, `nothing-detached@f807c7f5fcea`, `a-leaked-child-fails-its-test@9a82a5147ba6`, `never-break-an-existing-client@ed293965fc5c`, and the change `sluice-host-owns-its-workers`, design D1 to D11.

### Decisions

1. **Each worker is a child of `sluice host`, in a process group of its own, and records itself.** Before: the host process started each run's supervisor in a session of its own, and the supervisor continued after the host process ended. Now: a run's supervisor, a git command, a credential command, an equip step and a release command that the host process starts are each its child in a process group of its own. The child writes its record in `host/workers/` between its fork and its exec, so no work starts unrecorded. The record's name is the child's pid, and it holds the owner's pid and start time. A run's supervisor records the run's checks and watch for the same owner. *Not taken:* the process-wrap crate, because std's process group and the record before the exec do the same with no new crate; and tokio's `kill_on_drop` alone, which ends the direct child only.
2. **A stop ends the workers, and a run that ended so has no outcome.** Before: a stopped host process left its runs running, and the next host process read their results. Now: a stop by a signal or by a state folder that is gone sends `SIGTERM` to each child worker's group, and gives it 15 seconds. A run's supervisor that is told to stop ends its checks and writes no result. Then each group that a record names is ended, with weir-bounded's grace first. The run has no outcome, blames no one, and counts toward the runs in a row as a run whose claim lapsed.
3. **A lost run that names no check is tested again.** Before: a run on a branch that names no required check, which ended with no outcome, named no check with no outcome, and the core read it as passed. Now: such a run has every check of the run with no outcome, and its follow-up is given every check again. The stop of decision 2 makes such a run at each stop, so the core had to read it right.
4. **Every hand-over starts afresh in place.** Before: a host process that was no daemon ended when a newer command asked it to hand over, and a change of `[telemetry]` started a successor of another pid, detached. Now: each host process starts afresh in its own process, by `execve`, with the same pid. It carries its start lock and its socket, as a daemon did, so its workers stay its children. A newer command waits for a host process of another pid, or of the same pid with another `since`. Where the process it asked ends, as an older sluice's does, it starts its own. A host process still writes to `SLUICE_READY_FD` where an older sluice's host process hands over to it.
5. **A daemon that takes the host's place asks the host process to end.** Before: the daemon asked a hand-over, and the host process ended. Now: the daemon's `hand-over` carries `ends`, and the host process ends and its runs end with it, since a daemon is another process and cannot take them. The daemon tests their combinations again. A host process of an older sluice reads the request as a `hand-over` and ends, as before.
6. **A start ends what a killed host process left.** Before: nothing ended a supervisor whose host process was killed. Now: a host process that starts reads `host/workers/` before it claims a run or starts a worker. It ends each group of another owner that still runs, and waits again on each child that an earlier image of its own process started. A record is of a live worker only where its pid runs and started within two seconds of the record's write, so a pid that the system gave to another process is never ended.
7. **A new sluice is a hand-over, not a restart.** Before: the daemon's service ran the package's sluice, so a new package restarted it, and the restart left the runs with no owner. Now: the services run the system profile's sluice, so a new package changes no service. The launchd agent sets `AbandonProcessGroup` false, and the systemd unit sets `KillMode` `control-group`, so a stop ends the job's group. `hello`'s answer names the executable that the host process runs. `sluice hand-over` has a host process that runs another sluice start afresh as this one, and starts none. The activation runs it in place of a restart.
8. **A host process with a running worker is not idle.** Before: a host process that was no daemon ended once nothing was in play, while its runs continued. Now: it ends only once no child worker runs, since its workers end with it.
9. **A worker's end is an event at the edge.** Before: a run's end was found by the file events of its `result.json`, and the minute's backstop found a supervisor that ended with no result. Now: the host process waits on each child worker, and its end frees its part of the bound at once, whatever way the run ended. The registry's watch stays for a session's runs, which `sluice exec` starts.
10. **A test fails where it leaves a process.** Before: no test failed for a process that it left, and one `sluice host` of a test ran for 11 hours. Now: a guard in the test support finds a test's processes by its folders, by the sysinfo crate. Each scratch folder and each `OnDisk` holds one. The crates' test tasks run under cargo-nextest, whose `leak-timeout` reports a test that leaves a process holding its output and does not fail it: on macOS, nextest also names a test whose output pipe another test process inherited. The plugins' shell tasks and the check-e2e tier run under `tests/leaks.sh`, which runs the test in a process group of its own and reads with pgrep alone, since the gate's sandbox refuses `ps`.
