# A host's queues move in sluice's own host process, started when work arrives and gone when idle, and each branch's queue runs whole in one of four ways

## Context and problem statement

Record 0068 kept sluice a plain command line that needs no daemon and let a host run one driver, `sluice run`, by its own choice. A host that wants every queue moving runs one per repository; the gate box runs five under systemd, and the user called that design one that "just doesn't scale". Record 0092 proposed one host driver for every repository, still a service a host keeps. Meanwhile every waiting submit and wait on a host runs rounds where no driver lives, so ten agents' submits are ten processes each trying to form the branch's next candidate, and the host's bound on runs is counted across processes through files. And a branch that takes pull requests is taken in by whichever host holds an intake mark on the forge, with its renewal, its lease, hand-overs and their withdrawals.

## Considered options

1. **One host process, sluice's own.** The first command that needs the host's queues moved starts it where none answers; it holds every repository on the host that has sluice, each repository's queues apart, and the host's bound on runs in one place, and ends once no queue has work in play and nothing follows it.
2. Record 0092: one host form of `sluice run`, which a host's service manager keeps. One service in place of one per repository, but still a service each host installs and keeps.
3. One process per queue, started by its submit. Ten submits to ten branches are ten processes, and the host's bound and the forge's allowance are coordinated across them through files.
4. Every command runs rounds itself, as a waiting submit does today. Nothing new runs, but ten waits are ten processes forming one branch's candidate.

## Decision outcome

Option 1.

- **Nothing is installed.** sluice is a binary on the path. A command that needs the host's queues moved, a submit among them, reaches sluice's host process over a socket in sluice's state folder, or takes the lock and starts it when nobody answers. A submit adds its entry and returns at once; `sluice wait` follows the process for whoever wants to watch (135).
- **One process per user on a host.** It holds a task for each repository with work, each repository's queues apart, so a refusal or a slow fetch in one holds no other's round (26); one scheduler keeping the host's bound on runs, a queue's candidates before sessions' runs (71, 150); and one forge client, one allowance. Its concurrency is the language's, inside one process, never processes coordinating through files.
- **Gone when idle, and nothing lost.** It ends once no queue it holds has work in play and nothing follows it. It keeps nothing the records do not hold, so a crash or a sleeping laptop loses nothing: the next command that finds work in play and no host process starts one. It finds its repositories in an index sluice writes in the host's state whenever any command of sluice's finds a repository has sluice, a policy at a revision the host holds or records, the user's choice. A run outlives the process that started it and is equipped from its repository's policy (147). A command of a newer sluice has an older process hand its repositories over and end (135).
- **The reader is the host process.** A watch or a wait that finds no reader starts the host process, which reads, and follows it (129).
- **No intake mark.** The intake mark, its renewal and lease, hand-overs and their withdrawals all go (120, 140). Whatever executes a branch's queue takes its requests in. A host's submit opens or updates its request and marks it ready, and the host follows it by the forge's state and sluice's check on its head, its status showing the request's entry there as fields (137, C.5).
- **Where a queue runs.** Each branch's queue runs whole in one of four ways, behind one contract with Flume, as the amendment of 2026-11-08 below has it.
- **sluice calls no other program.** Flume reads each outcome at its settles; its step per settle is nothing (flume C.6).

## Amendment of 2026-11-08: one contract with Flume, and a queue runs whole in one of four ways

sluice keeps one contract with Flume and the Boomdrive runner however a queue runs, and each branch's queue runs whole in one of four ways: with no daemon, by a daemon on this machine, by a daemon on another machine, or by a GitHub Action. Status: accepted by the user on 2026-11-08, on their card ("Approved"), and point 3 as it reads now on their card the same day ("Yes: machines choose how sluice runs, the repository says what must pass").

Deciders: the user, 2026-11-08, in agentplot-ops's pane, as agentplot-ops relayed it (signal 2026-11-08-agentplot-ops-134a1434/01). They asked for sluice's direction to be handled as two separate things. The first is how sluice works with Flume and the Boomdrive runner: `sluice submit` starts the background processes, and sluice reports to Flume when the work is done, so Flume marks it and launches a fix. The second is local against remote execution, which doesn't change the first: "It seems like the GitHub job idea, just for doing the pushes to main and not for running the test, is a [...] band-aid from a design perspective. In my mind there's going to be local execution and then there's going to be remote execution but that doesn't change."; "I think we need to support either a daemon running on the same machine or a different machine, or a GitHub action". The same day, refining it (signal 2026-11-08-agentplot-ops-77e3a93c/01-sluice-runs-four-ways): "I'd argue that it's really four options because sluice runs on the same machine as a background process that gets kicked off. We did that to avoid the daemon but let's face it: a remote executor is a daemon. What stops you from running a daemon on the same host or a remote host? It's kind of the same thing but sluice should also be able to run without a daemon". Reading the plan that followed, the same day: "Why would it be the responsibility of a repository to know how its surrounding infrastructure is actually set up?" agentplot-design for writing it into this record and the statement, and for the choices marked as its own.

1. **Two concerns, kept apart.** How sluice works with Flume and the Boomdrive runner is one concern, and where a branch's queue executes is another. A change to one never changes the other.
2. **One contract, wherever the queue runs.** `sluice submit` adds its entry and returns at once, having started whatever background work the way that executes its branch needs. Once the submission is decided, sluice reports its outcome to its submitter as this record has it (the notice, `sluice inbox` and `sluice wait`), and Flume reads that report, marks its place, and launches the kind's landing fix on a kick-back (flume record 0056; weir record 0005). sluice still calls no program of Flume's. The user's "sluice report" is this report. Whether it is also a command of its own is the build's choice, and it changes nothing of the contract.
3. **A queue executes whole, in one of four ways, and the machines choose it.**
   - **No daemon.** The submitting machine's own sluice process executes it: `sluice submit` starts it, and it ends when idle (135, as decided above). sluice works this way with nothing set.
   - **A daemon on this machine.** The machine keeps `sluice daemon` running. That is the same host process, which never ends when idle.
   - **A daemon on another machine.** That machine keeps `sluice daemon` running, and it runs the queues of the repositories it holds.
   - **A GitHub Action.** GitHub Actions' jobs execute it: they take the requests in, run the checks on GitHub's machines and push the landing. The repository carries the workflow GitHub runs. This is the one thing any way puts in a repository, since GitHub runs only jobs a repository defines.

   No setting chooses a way. A daemon is a command a machine keeps running by its own choice. The repository says only what a landing must pass and whose test results it accepts: its gate and its signers. Those stay in the repository because a machine can't vouch for itself, and the branch's own revision is what is read, so no change loosens its own checks (core.15, 78). A shared branch's queue runs where its results count. A machine whose signature the branch does not accept leads none of its rounds and runs none of its checks. It submits, and leaves the queue to one whose signature the branch accepts.

   Whatever executes a branch's queue takes its requests in, forms and tests its candidates, and lands them. Nothing does one part of that while another does the rest. No request is taken in by two ways, two machines or two copies of one repository.
4. **Not taken.** A forge's jobs taking requests in and landing them while machines run the checks, the split the user called a band-aid. A branch on GitHub Actions runs its checks there too, and the change that built the split is reverted whole on its bolt (`sluice-runs-one-host-process--takes-out-the-forge-round`).
5. **What stands.** Everything else above stands: one host process per user, started when work arrives and gone when idle, as the no-daemon way, with nothing installed on a machine that uses it. So does the removal of the intake mark, its renewal, its lease and its hand-overs. Whatever executes a branch takes its requests in.
6. **Consequences.**
   - sluice runs standing only as a daemon a machine keeps running by its own choice, on this machine or another (point 3). That settles wldn's question of a machine whose signature a branch's tests need: that branch executes by a daemon on that machine, which stays up.
   - Rules core.31 and core.33 are amended to match, each marked proposed.
   - The statement's clauses 135 and 137 and C.8's table follow, marked proposed (agentplot/blueprints, design/sluice/requirements.md).
   - Left to the build, within points 2 and 3 (agentplot-design's choice): how a machine's service manager keeps `sluice daemon` running, and what a machine whose signature a branch does not accept starts when it submits. Units are queued from this amendment.

## Amendment of 2026-11-13: every read of a queue follows the host process, and a result is read once

agentplot-design's, drawn from clauses 69, 109 and 129. On chuck-herdr-alpha under sluice 0.93.2, each one-shot overview fetched its repository from the remote under one lock and loaded the whole results history, about 60 MB, so waits that read it missed their 10-second bound (signal 2026-11-13-swb-7-ops-ca607be7/01, wldn's).

- **Every read follows the host process.** A status, an overview and a forecast are answered from the host process's last reading, as a watch and a wait are, and fetch nothing of their own while it has read within its tick. One that finds no host process starts it and is answered from its first reading. The remote is asked once a tick for every branch the host reads there (129). Record 0056's one-shot overview, which read the records itself, is amended so.
- **A result is read once.** The host process reads each recorded result and each signed run record once, verifying each signature once, and answers a gate or a status by the keys it asks for. No read loads or verifies the whole history again, so a read costs what it asks for, however long the history grows.
- **No result is taken away with its branch.** A result belongs to its key and system, not to a branch (69); a signer's records are only added to (109); a landing reads its verdict again from them (C.6). A branch that lands or is removed keeps every result it recorded. Pruning a landed branch's results was the other path: it would take away passes other branches' gates count and evidence a landing names.
- Rule core.25 is amended to match.

## Amendment, 2026-11-13: what the build of the host process chose

Status: accepted on 2026-11-13 as the choices of the change `one-sluice-process-runs-each-hosts-queues`, its design D1 to D17 and its code stage, each within the decision and its amendments above and cheap to change.

Deciders: the design and the code stage of the change `one-sluice-process-runs-each-hosts-queues`.

Sources: the statement's clauses 64, 69, 71, 88, 109, 129, 133, 135 and 150, S19 and S75; records 0063, 0087, 0107, 0119 and 0123; rules core.4, core.22, core.25, core.29, core.31 and core.49; the change's design D1 to D17; `crates/sluice/src/host_process/`, `crates/sluice/src/profiles/records.rs` and `crates/sluice-core/src/step.rs`.

### Decisions

1. **The socket is in the user's own short directory** (D1). The host process binds `host-<digest>.sock` in the user's directory that record 0063 makes and checks, named by a digest of the state folder's real path, so each state folder has its own process and no socket's path passes macOS's 104 bytes however deep the state folder lies. *Not taken:* the socket under the state folder's `host/`, as the decision words it, which a test's or a sandbox's deep state folder makes too long to bind.
2. **`sluice run` is kept, hidden, as a follower** (D11). It checks the host's systems, says once on stderr that sluice starts its own host process and nothing needs it, and prints each pass of the host process as a pass of its own printed it; `--rounds` counts the passes it followed. It takes up a change of `[telemetry]` alone, by starting itself afresh, carrying the passes it followed and what it said. *Not taken:* removing the command, which turns each host's unit that runs it into a restart loop until the unit is retired; dropping its take-up, which leaves a follower sending to a collector the file no longer names.
3. **`sluice step` is the host process's round** (D10). The step asks the host process for one round of the branch, which runs between the repository's passes, and prints the document a step printed. *Not taken:* a step that runs its round in its own process beside the host process's passes, two processes acting on one branch's round loop (core.14).
4. **Passes when asked, for the tests** (D14). Under `SLUICE_ROUND_SLEEP=record`, the value the tests already set to skip pauses, the host process takes no pass of its own and passes only for a `pass` or a `step`; its `hello` says so, and a follower then asks a pass at each of its own ticks, whatever its own setting. *Not taken:* a setting that keeps the host process from starting, with waits running rounds as before, a behaviour 135 removes kept behind a flag (core.12); a follower reading the mode from its own environment, which leaves a watch of a host process an earlier test command started reading nothing new.
5. **The look runs on a thread of its own for each repository** (D4). At its start and every three seconds the host process looks at each repository in its index it holds no task for, each look on a thread of its own under the round's retry policy, never on the loop that accepts connections; a repository still being looked at is passed by. *Not taken:* the looks on the accepting loop, where a remote slow to answer holds every command's connection.
6. **A newer command waits out an older process's hand-over** (D8). A command whose version is newer asks the older process to hand over, then waits for its lock to go for as long as the process gives its tasks to finish their rounds and a start's ten seconds after, and only then starts its own; an older process still running then is an error naming its log. *Not taken:* a start's ten seconds alone, which an older process still finishing a round outlasts.
7. **A part is held from the count to the start, and a start refused at the bound starts nothing further** (D12). A round holds each run's part of the host's bound before it writes the decision that marks the run starting, keeps its parts through its landing, releases and outcomes, and hands each to its start; a start the check seam refuses at the bound opens again each run decided behind it, its part dropped and no place made. A run a lead marks starting under the claim it gives a pool's job holds no part of the lead's host: the job's own round holds its run's part as it starts it, and a run launched on a pool holds none at all. The check seam's `hold` names no repository: the check profile is bound to its repository and names it to the host's room. *Not taken:* the room counted when the round decides and admitted only at the start, the two steps the decision ends; a pool's run counted against the lead's host, which it never runs on.
8. **Each repository keeps its own forge client.** Each repository's task binds the repository afresh, its forge client among it; the allowance's pause stays one for the host, in the host's state (134; rule core.29). *Not taken:* one forge client shared by every repository's task, a change of its own.
9. **A records list the pass cannot read is the reader's document.** A pass whose read of the branches' records fails writes the failure, in the words it was refused with, as the document every watch and wait follows, and reads the records again at its next pass. *Not taken:* failing the pass, which leaves every follower reading the last document as though nothing failed.
10. **A one-shot read sends `read` and reads held** (D16). A status in each form, a one-shot overview, the home view and a forecast where no reader keeps its tick send `read {repository}`, starting the host process where none answers, and then read with the core held: every branch through the records as the host holds them since the host process's last ask, the branch's revision with no fetch, the records seam's `hold` listing the branches and the hosts' signs of life from what that ask fetched, and a round refused under it. *Not taken:* running the read inside the host process over the task's binding, which holds a read behind a landing for minutes and sends its warnings to the host process's log; a read that fetches for itself where the reading is stale, today's cost.
11. **A reading is marked as it begins and ends, spanning a pass** (D16). Each pass and each look marks the repository's reading as it begins and as it ends, with the words a remote refused it with. A reading is current where it ended within a tick, three seconds, or where one under way began within a tick of the last one's end, so a status during a long landing is answered at once from the reading before it. Where none is current, the task's next pass reads, woken at once, or the look where no task runs; under passes when asked, the look, which runs no round. *Not taken:* a reading current only once ended, which holds every status behind a landing.
12. **A read waits the round's retry bound and a tick** (D16). The host process waits for the reading it asked for for the round's retry bound and a tick, and the command for that and a tick more; past it, the command reads as the host holds the repository and says on stderr when the host process last read it. A current reading whose ask a remote refused is said on stderr in the remote's words, the records read as last fetched. *Not taken:* waiting without end for a host process held in a look a remote does not answer; reading held with nothing said, which hides that the remote could not be asked.
13. **A one-shot overview prints the records as the host holds them.** A look writes no reader's document, so the overview and the home view render the records as the host holds them since the reading, with the pull requests as the host last kept them, as the watch renders its document. *Not taken:* a look that writes the reader's document, which takes the reader's lease from a pass.
14. **A forecast forms on what the host holds, and asks afresh once** (D16). A forecast with no current reader forms from the reader's document where the reading's pass wrote one, and otherwise on the records and the branch as the host holds them, fetching nothing; where the host lacks the branch, a revision it forms from or work queued on it, it sends `read` with `afresh`, answered once a reading begun after the ask ends, forms again, and says what is still lacking as a read it could not make, exit 3. *Not taken:* fetching what is lacking, the cost the reading removes.
15. **Results are asked for by what the caller reads** (D17). `State::results_for(branch, &ResultAsk)` answers every line whose key, combination or task the ask names; a landing's second reading asks the combinations it lands, then their keys, which a pass elsewhere may prove. An ask for every line is kept for a test's inspection of the log, which no step, gate or command makes. *Not taken:* a way for each test's rig to read its log whole beside the seam.
16. **The host process keeps an index for each results log** (D17). One for the repository's own log and one for each remote's replays beside it, kept for the process's life and found by the log's path, each read from its offset, read whole again where the file shrank or was replaced, and each signer's ref read by entry, a blob verified once for each key digest. The tick's ask fetches each signer's runs, and a push of a signer's runs is read here as fetched, so a round reads its own signed runs with no fetch. Each answer that verified a record says how many in the host process's log. *Not taken:* one index holding every log of the repository; a fetch of the signer's ref at each read, which a command made before.
17. **A command asks with `results`, answered on the connection's thread** (D15, D17). A command's records profile sends `results {repository, branch, wants}`; the host process answers on the connection's own thread from its index, through a binding of its own that reads every remote as the last ask fetched it, with no wait on the repository's task. A command whose host process cannot be asked reads the results itself and says so on stderr. `sluice status <n> --json` gives `checks`, the rows of the combination the submission was last tested in, read from that combination's results alone. *Not taken:* answering through the repository's task, which holds a status behind a pass; failing a command whose host process cannot be asked, which a host process of an older sluice that knows no `results` would make every such command do.
